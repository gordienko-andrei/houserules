# Houserules — устройство продукта и развитие правил

## Назначение

Houserules помогает Angular-команде описать, как её дизайн-система отображает данные, и передать эти соглашения разработчикам и AI-агентам. Конфиг связывает роль данных с компонентом или pipe проекта. CLI создаёт короткие инструкции для агента и выдаёт подробности по выбранным ролям. ESLint обнаруживает поддерживаемые нарушения в шаблонах и показывает пример исправления.

Пример роли денег задаётся в `houserules.config.ts`.

```ts
import { defineConfig } from '@andrewgordienko/houserules';

export default defineConfig({
  preset: 'recommended',
  roles: {
    money: {
      component: 'ui-money',
      usage: '<ui-money [value]="$value" />',
      files: 'src/app/ui/money/**',
    },
  },
  currencyWords: ['руб.'],
});
```

`component` — это селектор: кастомный элемент (`ui-money`) или директива на элементе (`button[mat-flat-button]`, `button[pButton]`). Так роль работает с библиотеками, где дизайн-система живёт в директивах.

`$value` обозначает выражение, которое подставляется в пример. `files` исключает собственные файлы компонента из денежного правила, чтобы он мог форматировать значение внутри себя. У роли задаётся один `component` или один `pipe`. Для пользовательской роли также нужно описание `description`.

## Как устроены пакеты

| Часть | Ответственность |
| --- | --- |
| `packages/cli`, пакет `houserules` | Схема конфига, команды, сканирование, проверка роли, генерация инструкций, общие настройки правил и конфиг stylelint |
| `packages/eslint-plugin` | Реализация шести ESLint-правил и фабрика flat config `configs.recommended()` |
| `playground` | Небольшой проект с корректными и намеренно ошибочными шаблонами |
| `field-tests` | Запуск на закреплённых версиях реальных проектов и сохранение отчётов |

Плагин зависит от пакета `houserules` и использует его разрешённые настройки. Этот же результат использует генератор инструкций и команда `validate`. Текущие публичные API экспортируются из `packages/cli/src/index.ts`.

## Путь команды

1. Установите `houserules`, `eslint-plugin-houserules`, ESLint и `@angular-eslint/template-parser`. Требования и вариант установки из локальных tarball описаны в [руководстве установки](guide.md).
2. Выполните `npx houserules init`. Команда создаст конфиг, управляемую секцию `AGENTS.md`, импорт в `CLAUDE.md` и навыки для Claude.
3. Выполните `npx houserules scan` или `npx houserules scan --json`. Проверьте найденные компоненты, pipe и примеры вызовов в исходном коде. Укажите подходящие роли в конфиге.
4. Выполните `npx houserules validate`, затем `npx houserules generate`. После изменения конфига повторяйте обе команды.
5. Подключите правила в flat config ESLint.

```js
import houserules from 'eslint-plugin-houserules';

export default [
  // Другие блоки проекта.
  ...houserules.configs.recommended(),
];
```

При запуске ESLint из другого каталога передайте `{ cwd: import.meta.dirname }`. Для CSS и SCSS подключите отдельно `@andrewgordienko/houserules/stylelint`, как показано в руководстве установки.

Агент сначала запускает `npx houserules context --list`, затем выбирает нужные роли командой, например,
`npx houserules context --roles money,status`. Команда возвращает выбранные примеры и общие правила.
Добавьте `--project`, чтобы получить глоссарий и пути к примерам проекта. Если роль не подходит, доступна команда `context --guidance`. Неизвестная роль
вызывает ошибку и предлагает посмотреть список. Подбор ролей выполняет агент на основании задачи и контракта данных.

Для CI используйте `npx houserules validate`, `npx houserules generate --check`, ESLint и при необходимости stylelint. `generate --check` возвращает ошибку, когда содержимое генерируемых файлов устарело.

## Как работает конфигурация

`preset: 'recommended'` задаётся новым конфигам через `init`. В нём денежное правило включается при наличии роли `money`, `no-px-font-size` работает как ошибка, `require-async-states` как предупреждение, а `no-glued-fields` выключено. `strict` включает все применимые правила на уровне ошибки. Конфиг без `preset` сохраняет прежние строгие уровни. Поле `rules` позволяет явно задать `off`, `warn` или `error`.

Роль даёт агенту пример использования. Само её наличие включает автоматическую проверку только там, где для роли реализовано правило. Сейчас такое правило есть для `money`, а для любой роли с компонентом — проверка `replaces`. Роль может описывать не только значение, но и шаблон интерфейса: пользовательская роль с `description` и полным `usage` передаёт агенту набор свойств, который команда задаёт всегда. Другие роли используются в инструкциях, а некоторые из них добавляют примеры в сообщения `no-glued-fields`.

`scan` ищет исходники в существующих `src`, `apps`, `libs`, `projects` и каталогах `sourceRoot` из `angular.json`. Явный `scan: { roots: ['apps', 'shared'] }` выбирает каталоги относительно корня проекта. Если известные каталоги отсутствуют, сканер обходит корень с исключением служебных каталогов. Отчёт включает корни, число шаблонов, ошибки разбора, примеры использований и отсутствующие зависимости.

`validate` проверяет схему, ищет объявление роли и проверяет синтаксис `usage` и точное имя элемента или pipe. При установленном плагине пример также проверяется правилами Houserules. Обнаруженные использования без объявления, неоднозначные объявления и неполная область поиска показываются как предупреждения. Проверка синтаксиса и декларации не определяет доступность компонента в imports конкретного экрана и не проверяет бизнес-смысл данных.

## Действующие правила и пределы их проверки

| Правило | Что обнаруживает | Границы |
| --- | --- | --- |
| `use-money-component` | Настроенные денежные pipe и выражения рядом с маркером валюты | Не определяет тип каждого выражения и не охватывает все способы ручного форматирования |
| `no-glued-fields` | Поддерживаемые варианты соединения значений разделителями и стрелками | Работает по синтаксическим шаблонам и не оценивает весь контекст интерфейса |
| `require-async-states` | Вызовы API Angular resource в одном шаблоне | Вызов `status()` считается обработкой загрузки и ошибки. Состояния в родителе, обычные сигналы и подписки не видны |
| `no-px-font-size` | Размеры шрифта в `px` во встроенных стилях шаблона | CSS и SCSS проверяет отдельно конфиг stylelint |
| `prefer-role-component` | Нативные элементы из `replaces` роли, например `button` | Включается только при `replaces`. Элемент с нестандартным атрибутом считается обработанным директивой и пропускается. Связанное значение `[type]="x"` считается неизвестным, и правило в таком случае молчит |
| `restricted-template-syntax` | Узлы шаблона, подходящие под селекторы из `restrictions` | Включается только при `restrictions`. `validate` проверяет примеры `bad` и `good` |

### `replaces` или `restrictions`

Если запрет звучит как «вместо этого нативного элемента используй компонент роли», это `replaces` у роли. Сообщение берёт `usage` роли, а элементы с директивами пропускаются. Всё остальное — `restrictions`: селектор ESLint по AST шаблона, сообщение и примеры. Оба механизма проверяются одинаково: `validate` прогоняет линтер по примеру нарушения (для `replaces` он строится из селектора) и по правильному примеру (для `replaces` это `usage` роли).

Основная фабрика ESLint по умолчанию применяется к `**/*.html`. Сканер также собирает поддерживаемые inline-шаблоны, но покрытие inline-шаблонов линтером зависит от конфигурации проекта. Зелёный результат линтера означает, что обнаруживаемые конструкции прошли включённые проверки.

## Как добавить правило

Начинайте с поведения, которое можно наблюдать в шаблоне. Зафиксируйте примеры нарушения, корректные и пограничные случаи, ожидаемое сообщение и ограничения. Если вывод зависит от бизнес-смысла, который недоступен парсеру, сформулируйте проверяемый синтаксический случай и выберите соответствующий уровень строгости.

1. Создайте реализацию в `packages/eslint-plugin/src/rules/<имя>/rule.ts`. Используйте существующие `createRule`, проверки парсера и вспомогательные функции AST. Укажите схему опций и сообщение, по которому человек или агент сможет исправить пример.
2. Добавьте тесты правила через существующий `RuleTester`. Покройте корректные шаблоны, нарушения, сообщения, опции и случаи, похожие на нарушение. Если исправление нельзя гарантировать, оставьте его ручным.
3. Зарегистрируйте реализацию в `packages/eslint-plugin/src/index.ts` и имя в `RULE_NAMES` в `packages/cli/src/config/schema.ts`.
4. Добавьте профильные уровни, условие роли и краткое описание наблюдаемого паттерна в `packages/cli/src/config/rule-metadata.ts`. Добавьте правило и его опции в `candidateRules` в `resolve-rules.ts`. Для правила, зависящего от роли, передавайте нужные значения конфига и исключения файлов.
5. Добавьте страницу `packages/eslint-plugin/docs/rules/<имя>.md` с примерами, опциями и ограничениями. При необходимости добавьте отображение правила в генерируемых инструкциях и тест, который проверяет поведение при `off`, `warn` и `error`.
6. Проверьте интеграцию через `configs.recommended()`, генерацию `AGENTS.md` и `validate`. Для нового пользовательского сценария добавьте пример в playground и воспроизведите его в тесте.
7. Запустите `pnpm test`, `pnpm typecheck` и `pnpm playground`. Последняя команда завершается кодом 1 из-за намеренно ошибочных примеров. Сверьте состав ошибок с `playground/README.md`.
8. На подходящих полевых проектах выполните `pnpm field-test films` и `pnpm field-test ghostfolio`. Разберите срабатывания и пропуски в review-файле проекта. Добавьте тест на каждый обнаруженный случай, который решено поддерживать.

Общий каталог метаданных типизирован по `RuleName`. Интеграционный тест сопоставляет его ключи с экспортами плагина. Изменение поведения по умолчанию влияет на существующие проекты, поэтому учитывайте версии, профиль и миграцию.

## Масштабирование

Для новых ролей сначала используйте конфигурацию `roles`, описание и реальный пример вызова. Добавляйте линтер, когда у нарушения есть достаточно надёжный распознаваемый признак. Предпочитайте точное сообщение с примером и начальный уровень `warn`, если правило опирается на эвристику.

Для больших репозиториев ограничивайте область `scan.roots` нужными каталогами. Обрабатывайте каждый файл один раз, храните счётчики и ограниченное число примеров. Не увеличивайте вывод `scan --json` всеми неиспользуемыми экспортами зависимостей. При оптимизации сравнивайте число найденных использований и результаты до и после, а также время и память на одном исполнителе. В [ExecPlan](exec-plan-reliability.md) записаны имеющиеся результаты и границы замеров.

Постоянный дисковый кеш имеет смысл оценивать после измерений повторных запусков. Его инвалидирование должно учитывать изменения файлов, зависимостей, версии парсера и области поиска. Держите правила независимыми друг от друга, общие метаданные — в пакете `houserules`, а конкретные обходы Angular AST — в плагине. Это позволяет добавлять правила без отдельной несогласованной конфигурации для генератора и ESLint.

## Полезные команды разработчика

```sh
pnpm install
pnpm test
pnpm typecheck
pnpm playground
pnpm field-test films
pnpm field-test ghostfolio
```

Для управления примерами используйте `node packages/cli/dist/cli.mjs validate --cwd playground` и `node packages/cli/dist/cli.mjs generate --check --cwd playground` после сборки.
