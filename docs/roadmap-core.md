# Дорожная карта ядра Houserules

Состояние на 23 ноября 2026 года. План описывает путь от текущего MVP до ядра, которое закрывает большинство AI-slop паттернов в скоупе продукта. Скоуп и слои взяты из брифа: Houserules отвечает за представление данных и обратную связь. Навигация, раскладка страниц, формы, анимация и общий «beautify» остаются вне ядра.

## Граница: когда ядро готово

Ядро считается готовым, когда выполнены все пять условий.

1. **Покрытие каталога.** Не меньше 80 % паттернов из каталога ниже закрыты линтером (L) или ролью с инструкцией (C + S). Остальные явно помечены как вне ядра с причиной.
2. **Точность на чужих дизайн-системах.** Каждое правило уровня `recommended` даёт не меньше 90 % верных срабатываний на трёх полевых проектах с разными дизайн-системами: PrimeNG, Angular Material и Taiga UI. Конфиг любой из них описывается без обходных решений.
3. **Доказанный эффект.** Бенчмарк «агент без Houserules / с ним» показывает меньше нарушений и меньше обходов правил при сопоставимом числе итераций.
4. **Настройка без ручной работы.** На новом проекте агент по навыку `houserules-setup` собирает рабочий конфиг за один сеанс, человек только подтверждает. Навык `houserules-learn` превращает правки ревью в конфиг.
5. **Готовность к использованию.** Пакеты опубликованы в npm, есть CI с матрицей версий парсера шаблонов и ESLint, changelog и документация для каждого правила.

Всё, что после этой границы, перечислено в разделе «После ядра».

## Каталог AI-slop паттернов и покрытие

Обозначения: **L** — проверка линтером, **C** — роль в конфиге, **S** — правило в навыке или контексте агента.

| # | Паттерн | Пример | Механизм | Сейчас | Чего не хватает |
| --- | --- | --- | --- | --- | --- |
| 1 | Значения склеены разделителями | `{{ symbol }} · {{ currency }}` | L + C `metric` | Есть: `no-glued-fields`, включая разделитель внутри `@if` | Цепочка `@if` после `@if`. Тире не проверяем: диапазон от склейки не отличить |
| 2 | Изменение показано стрелкой в тексте | `{{ old }} → {{ new }}` | L + C `comparison` | Есть | — |
| 3 | Шаги через стрелки | `Откройте → проверьте → оплатите` | L + C `steps` | Есть | — |
| 4 | Деньги отформатированы вручную | `{{ total \| currency }}`, `{{ sum }} руб.` | L + C `money` | Есть: `use-money-component` | Сумма и валюта в разных элементах. Форматирование, унесённое в `.ts` |
| 5 | Даты, проценты и числа отформатированы по месту | `{{ d \| date: 'dd.MM' }}`, `toFixed(2)` | L + C | Нет | Обобщить денежное правило до роли с форматом: `date`, `percent`, `number` |
| 6 | Нативный элемент вместо компонента дизайн-системы | `<button>` при `<p-button>` | L + C `replaces` | Есть: `prefer-role-component`, роли на директивах, пропуск элементов с директивами | Обнаружение директив в `scan` |
| 7 | Нет состояний загрузки, ошибки и пустоты | `@for (x of items.value())` без веток | L | Только Angular `resource` | `async` pipe, `Observable`, сигналы из сервисов, `@defer` |
| 8 | Ошибка и пустое состояние — голый текст | `<p>Не удалось загрузить</p>` и нативная кнопка «Повторить» | L + C `issue` | Только S | Если роль `issue` есть, ветка ошибки показывает её компонент |
| 9 | Статус текстом или только цветом | `<span class="red">{{ status }}</span>` | C `status` + S | Только C + S | Правило «тон только цветом» (WCAG 1.4.1) — исследовать |
| 10 | Шаблон переписывает данные бэкенда | `message.split(':')[1]`, `text.slice(0, 80)`, `price - coupon` | L (warn) | Только S | Правило data fidelity: строковые и арифметические операции над данными в шаблоне |
| 11 | Тексты зашиты в шаблон | `<h2>Журнал изменений</h2>` в проекте с i18n | L (opt-in) | Только S | Включать, только если в проекте есть механизм i18n |
| 12 | Фиксированные `px` в шрифтах | `style="font-size: 12px"` | L + stylelint | Есть | — |
| 13 | Один компонент роли вызывается по-разному | `p-table` с разными наборами свойств на экранах | C (`usage`) + отчёт | Только C | `validate` показывает расхождения вызовов с `usage` |
| 14 | Текстовая ссылка вместо действия рядом с данными | `<a>Открыть заказ</a>` в строке таблицы | C `action` + S | Только C + S | Линтер не нужен: это решение продукта |
| 15 | Зелёный до факта успеха | «Строки корректны» зелёным до импорта | S | Только S | Не проверяется синтаксически, остаётся в навыке |
| 16 | Доступность действий | кнопка-иконка без `aria-label`, `(click)` на `div` | Интеграция | Нет | Не дублировать: рекомендовать правила `@angular-eslint/template` в документации и `init` |

Сейчас полностью закрыты 5 паттернов (1–4, 12) и частично ещё 2 (6, 7). Чтобы выйти на 80 %, ядро должно закрыть паттерны 5–11 и 13. Паттерны 14 и 15 остаются в навыке, паттерн 16 закрывается интеграцией.

Новый паттерн попадает в каталог по правилу трёх из брифа: он встретился минимум в трёх разных проектах или сценариях. Эксперимент с журналом аудита ([`assets/campaign-audit-changelog.md`](../assets/campaign-audit-changelog.md)) — первый такой источник: паттерны 6, 8, 10 и 13 в нём уже есть.

## Принципы, которые держат ядро универсальным

- **Ни одной библиотеки в коде.** Все конкретные компоненты задаёт конфиг проекта. Тесты используют PrimeNG, Material и Taiga только как примеры данных.
- **Новое правило проходит тест брифа.** Его можно объяснить незнакомому разработчику без ссылки на вкус, через WCAG, эвристики NN/g или инженерную корректность. Иначе оно идёт в пресет `clarity`.
- **Двусмысленный признак не становится ошибкой.** Если шаблон не позволяет отличить нарушение от нормы, как с тире, правило молчит или работает как `warn` с явными границами в документации.
- **Точность проверяется до включения.** Правило попадает в `recommended` только после полевых проектов и разбора в `review.md`.

## Этапы

Этапы идут по порядку: каждый следующий начинается, когда у предыдущего выполнен критерий готовности. Это соответствует правилу брифа «фаза начинается после эффекта на бенчмарке».

### Этап 0. Стабилизация текущей работы — выполнен

- Работа ноября разложена по коммитам на ветке `feat/core-roles`.
- Решение по `replaces` и `restrictions` принято: оба механизма остаются, проверяются одинаково через примеры, а правило выбора записано в `docs/product-and-rule-development.md`.

### Этап 1. Бенчмарк и демо — закрытие MVP

Бриф ставит бенчмарк в MVP, а без него нельзя доказать эффект ни одного следующего этапа.

- Демо-проект на свежем Angular с сигналами и `resource`: экран итогов массового импорта с ошибками из брифа, плюс экран журнала изменений по мотивам эксперимента.
- Набор из 5–8 задач на вёрстку с фиксированными промптами.
- Скрипт прогона: два режима (без Houserules и с ним), один агент, сбор результатов в каталог.
- Метрики из брифа: нарушения на экран, обходы правил (ручная разметка: `eslint-disable`, убранный знак валюты, форматирование в `.ts`), доля компонентов проекта, число итераций, токены и время.
- Отчёт с цифрами и наглядными «до/после».

**Готово, когда** есть воспроизводимый прогон и отчёт, а режим с Houserules лучше хотя бы по нарушениям и обходам.

### Этап 2. Точность механизма ролей на трёх дизайн-системах

Цель — убедиться, что механизм не заточен под одну библиотеку.

- **Обнаружение директив в `scan`.** Сейчас `scan` перечисляет только кастомные элементы, поэтому навык настройки не видит `pButton` и `mat-flat-button`. Нужно выводить атрибутные директивы из проекта и библиотек со счётчиками и примерами.
- **Исключение директив в `replaces` — выполнено.** Элемент с атрибутом, которого нет в HTML и среди директив Angular, считается обработанным директивой и пропускается. `validate` показывает по каждому селектору, сколько элементов он ловит и какие директивы пропущены. Замер на Ghostfolio с `replaces: 'button'`: из 167 кнопок правило сообщает об одной (область перетаскивания файла), 166 пропущены. До этого ручной список `:not(...)` давал 5 ложных срабатываний. На Films нативных кнопок нет, `input[pInputText]` пропущен.
- **Третий полевой проект на Taiga UI.** В нём деньги через pipe `tuiAmount`, кнопки через `button[tuiButton]`.
- **Разбор `review.md`** для каждого проекта и правила.

**Готово, когда** на Films (PrimeNG), Ghostfolio (Material) и проекте на Taiga конфиг описывается полностью, а точность `prefer-role-component` и `use-money-component` не ниже 90 %.

### Этап 3. Декларативные запреты — реализован, ждёт проверки на проектах

Фаза 2 брифа: проектные правила записываются данными, а не кодом.

- Блок `restrictions`: селектор ESLint по AST шаблона, сообщение и примеры `bad`/`good`. Выполнено.
- `validate` прогоняет линтер по примерам и отклоняет запрет, если `bad` не даёт ошибку или `good` нарушает правила. Для `replaces` пример нарушения строится из селектора. Выполнено.
- Отдельное правило `houserules/restricted-template-syntax`, чтобы не затирать собственные `no-restricted-syntax` пользователя в flat config. Выполнено.
- `houserules-learn` предлагает `restrictions` для запретов без роли. Выполнено в тексте навыка.

**Осталось:** записать запреты из эксперимента и полевых проектов в `restrictions` и убедиться, что `learn` предлагает их сам на реальном диффе.

### Этап 4. Расширение правил по каталогу

Каждое правило проходит полный цикл: тесты, страница документации, playground, полевые проекты, `review.md`. Порядок — по частоте паттерна и надёжности признака.

1. **Роль с форматом (паттерн 5).** Обобщить `use-money-component` в механизм «значение этой роли показывается только её компонентом или pipe». Затем добавить встроенные роли `date` и `percent`. Деньги остаются частным случаем с маркерами валют.
2. **Async-состояния шире `resource` (паттерн 7).** Сначала `async` pipe и `@defer`, затем сигналы из сервисов. Для нераспознаваемых случаев правило молчит.
3. **Ветка ошибки через роль `issue` (паттерн 8).** Если роль задана, ветка ошибки async-данных показывает её компонент.
4. **Data fidelity (паттерн 10).** Строковые методы (`split`, `replace`, `slice`, `substring`) и арифметика над данными в шаблоне. Только `warn` с понятным выходом: перенести в pipe или запросить поле у бэкенда.
5. **Зашитые тексты (паттерн 11).** Opt-in. Включается, только если `scan` нашёл механизм i18n (Transloco, ngx-translate, атрибут `i18n`) или он указан в конфиге.
6. **Расхождение вызовов роли (паттерн 13).** `validate` сравнивает реальные вызовы компонента роли с `usage` и показывает основные отличия.
7. **Интеграция с a11y-правилами angular-eslint (паттерн 16).** Документация и предложение в `init`.

**Готово, когда** покрытие каталога не ниже 80 %, а бенчмарк показывает, что новые правила снижают нарушения, а не прячут их.

### Этап 5. Audit и fix

Фаза 3 брифа: привести готовые экраны к ролям и компонентам проекта.

- `houserules audit`: отчёт по проекту, сгруппированный по ролям и паттернам каталога. Он же даёт «попутный отчёт» для команды.
- Навык `houserules-fix`: пошаговое исправление шаблона с проверкой, что набор `{{ }}`, `[prop]` и `(event)` до и после совпадает. При расхождении правка отклоняется.

**Готово, когда** fix на полевых проектах не меняет поведение шаблонов, а audit используется в демо «до/после».

### Этап 6. Выпуск 1.0

- Changesets, GitHub Actions, публикация в npm с provenance.
- CI-матрица: `@angular-eslint/template-parser` 17–22, ESLint 9 и 10.
- Пресет `recommended` заморожен: изменение уровней по умолчанию — только в мажорной версии.
- README с цифрами бенчмарка.

**Готово, когда** выполнены все пять условий из раздела «Граница».

## После ядра

Эти пункты есть в брифе, но не нужны, чтобы закрыть большинство паттернов:

- семантическая карта и `houserules infer` из TS-типов и OpenAPI;
- ревью по скриншоту;
- интеграции со Storybook MCP и Angular MCP;
- `houserules add` для проектов без своего компонента роли;
- пресет `clarity` со вкусом автора.
